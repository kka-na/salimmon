# 혼수 도장깨기 모바일 웹 — 개발 에이전트 작업 지시서

당신은 이 프로젝트의 **개발 전담 에이전트**입니다. 나는 별도의 **조사 에이전트**(ChatGPT)와 함께 가전·가구 브랜드, 모델, 실제 구매 가격, 사용 후기, A/S, 방문 가능 매장을 조사하여 Markdown 파일로 제공할 예정입니다. **당신의 업무는 앱 개발·데이터 파이프라인·UI/UX이며, 제품 정보를 임의로 조사하거나 만들어 넣는 것이 아닙니다.**

## 1. 목표

모바일에서 사용하는 귀엽고 완성도 높은 **혼수 도감 + 체험 지도 + 비교 노트 + 도장깨기 기록장**을 구현하세요. 카테고리는 침대부터 시작하지만 냉장고·세탁기/건조기·TV·소파·식탁·식기세척기·로봇청소기·청소기·에어컨·정수기 등으로 데이터 파일 추가만으로 확장되어야 합니다.

주요 사용자 여정: 카테고리 선택 → 브랜드/모델 카드 탐색 → 사진·가격·사양 확인 → 장단점·실구매 후기·A/S 펼쳐보기 → 지도에서 실물 전시점 찾기 → 찜/비교 → 방문·체험·구매 단계별 도장 찍기.

## 2. 아키텍처 (프런트/백엔드 반드시 분리)

- `client/`: **Next.js(App Router) + React + TypeScript + Tailwind CSS**. 필요 시 shadcn/ui, Lucide, Framer Motion 활용.
- `server/`: **FastAPI(Python) + Pydantic**, REST API 제공. 사용 기록 저장은 처음에는 SQLite를 사용하되 PostgreSQL로 이전하기 쉽게 구조화.
- `research/`: 조사 에이전트가 작성하는 **Markdown 원본 저장소**. 이곳이 제품·가격·리뷰·매장 사실의 유일한 원본(source of truth)입니다.
- `docs/`: 데이터 규격, 실행법, 구조, 근거·한계 설명.
- 서버는 Markdown의 YAML frontmatter + 본문을 읽고 검증·정규화하여 API로 전달합니다. 클라이언트에 브랜드·모델 데이터를 하드코딩하지 마세요.
- 기존 저장 데이터와 사용자 도장/메모를 보호한 채 새 MD를 추가·갱신할 수 있어야 합니다. 개발 시 파일 변경 자동 재읽기 또는 명시적 `import` 명령을 제공하세요.
- 클라이언트/서버 각각 `.env.example` 제공. 서버 키는 브라우저에 노출하지 마세요. 로컬 개발 실행 방식과 Docker Compose 실행 방식 문서화.

## 3. 연구 MD 계약

첨부된 `조사MD_작성규격.md`를 기본 명세로 사용하세요. 해당 문서와 모순 없이 필요한 필드를 확장할 수 있지만 **기존 필드를 조용히 변경하거나 삭제하면 안 됩니다.** `category`, `brand`, `model`, `store`, `review`의 다섯 entity를 지원하세요.

필수 규칙:

1. 모든 entity는 안정적인 `id`, `schema_version`, `entity_type`, `updated_at` 보유.
2. `model`은 브랜드/카테고리, 정확한 모델명, 매트리스·프레임 같은 상품 유형, 사진(없을 수 있음), 사양, 장단점, 가격 기록, 보증, 연결된 전시점/후기를 가짐.
3. 가격 기록은 `amount_krw`, `size_or_option`, `price_kind`(정가/할인가/구매자가 보고한 실결제가/과거가), `observed_at`, `source_url`을 함께 저장. 사이즈가 다르면 같은 가격처럼 표시하지 않음. 값이 없으면 '가격 미확인'.
4. 근거 있는 주장에는 출처 URL·확인일·출처 유형(공식/독립 사용자/판매자 등)을 붙임. 매장 주소·전시 여부·전화번호에는 `verified_at`과 `display_status`(전시 확인/매장만 확인/미확인)를 구분.
5. 리뷰는 `posted_at`, `source_url`, `purchase_evidence_level`(실사용 진술/구매·계약만/구매 인증 자료 있음/불명), `sponsorship_status`(무보상 확인/제공·협찬/불명), `usage_duration`을 기록. 협찬·제공 리뷰는 독립 후기 집계에서 제외. '내돈내산'이라는 글만으로 영수증 확인으로 간주하지 않음.
6. 사진은 `image_url`(사용 가능한 공식 이미지 또는 권리상 이용 가능한 경로)과 `image_source_url`, `alt`, `rights_status`를 함께 기록. 사진이 없으면 **중립적 플레이스홀더** 사용. 존재하지 않는 제품 이미지 생성, 이미지 무단 재호스팅 금지.
7. 위도·경도는 확인된 정보만 사용하며, 없는 경우 지도 SDK의 지오코딩을 이용하거나 주소 목록으로 대체. **좌표, 매장 영업 여부, 후기, 가격을 추측해서 채우지 마세요.**
8. 긴 서술형 Markdown 본문(시장 요약, 비교 분석, 제품 상세)은 그대로 보고서 뷰에서 읽을 수 있어야 함.
9. 유효하지 않은 MD는 조용히 누락하지 말고 경로·필드·오류 이유를 명시한 import validation report를 출력.

## 4. 화면과 기능

### A. 도감 홈
- 첫 화면은 '우리 집 혼수 도장깨기'라는 느낌의 차분하고 귀여운 모바일 UI. **파스텔, 손그림 스티커, 둥근 카드, 작은 도장 모션**을 사용하되 실제 정보 가독성이 최우선.
- 상단 가로 스크롤 카테고리 탭(침대, 냉장고, 세탁기 등), 검색, 브랜드/가격대/방문여부 필터.
- `카테고리 → 브랜드 → 모델` 탐색. 카드에 실제 모델 이미지, 브랜드, 정식 모델명, 종류(매트리스/프레임), 대표 가격+옵션+가격 확인일, 짧은 장점/주의점, 찜 상태 표시.
- 정보가 없는 카테고리/모델은 빈 상태로 보여주고 가짜 데이터를 채우지 않음.

### B. 제품 상세 도감
- 큰 대표 사진과 이미지 갤러리, 자세한 사양(침대라면 타입·경도·두께·규격·코일/폼 구조), 가격 히스토리, 옵션별 가격, 보증/A/S.
- 탭 또는 아코디언: `핵심 요약 / 장점 / 단점·주의 / 내돈내산 후기 / A/S / 출처`.
- 후기 원문 링크, 날짜, 사용 기간, 협찬 판정 상태, 구매 진술 수준을 표시.
- 같은 카테고리 최대 3종 나란히 비교 및 찜/후보 등록.
- 매트리스와 프레임은 별도 모델로 분리하고, 호환 규격이 확인된 경우에만 조합 추천.

### C. 실제 출몰지 지도
- 한국 지역에 적합한 **Kakao Maps JavaScript SDK** 우선 활용. 키가 없거나 SDK 로드에 실패하면 **주소·전화·외부 지도 길찾기 링크**가 있는 리스트로 정상 폴백.
- 매장 핀 클릭 시 브랜드, 주소, 전화, 전시 확인 상태/확인일, 전시 중이라고 근거가 있는 모델만 표시.
- 카테고리/브랜드별 지도 필터, 매장 목록 ↔ 지도 전환, 내가 방문한 매장 표시, 외부 지도 길찾기.
- 단순 입점 정보와 특정 제품의 실물 전시 확인을 혼동하지 않음. 위치 자동수집·자동 체크인은 MVP에 넣지 않음.

### D. 도장깨기 기록
- 모델별 `찜 → 체험 예정 → 체험 완료 → 최종 후보 → 구매 완료` 진행 상태. 매장에는 별도 `방문 완료` 도장.
- 각 모델마다 개인 메모, 직접 누워본 느낌/평점, 내가 받은 견적가·견적 날짜 입력 가능(이는 공식 조사 가격과 분리 저장).
- 카테고리별 진행률, 모은 도장, 방문 기록을 귀여운 스탬프북처럼 시각화.
- 새 MD 데이터를 다시 읽어도 개인 기록이 사라지지 않게 안정적인 ID를 사용해 SQLite에 저장.
- 로그인 없는 개인 로컬 MVP로 시작하되 추후 계정 추가 가능하도록 테이블 구조 분리.

### E. 모바일 사용성
- 360px 폭부터 잘 작동하고 한 손 조작에 편해야 함. 하단 네비게이션: **도감 / 지도 / 비교 / 내 도장**.
- 로딩·오류·자료 없음·출처 없음 상태 구현, 기본 접근성(버튼 레이블/키보드 접근), 작은 애니메이션. PWA 홈화면 추가는 여력이 되면 구현.
- 시각적 완성도는 높이되 장식이 제품 비교/출처 확인을 방해하지 않도록 함.

## 5. API와 데이터 처리

최소 API: `GET /api/categories`, `GET /api/brands`, `GET /api/models`, `GET /api/models/{id}`, `GET /api/stores`, `GET /api/reviews`, `GET /api/research/{category_id}`, `GET/PUT /api/progress`, `GET/PUT /api/personal-notes`, `GET /api/health`.

- 모델 및 매장의 카테고리/브랜드 필터와 검색 지원.
- Markdown 동기화/검증 CLI (`server/scripts/import_research.py` 등) 구현.
- 프런트는 API를 통해서만 데이터 수신. Markdown을 프런트 빌드에 고정 포함하지 않음.
- `last_verified_at`을 표시하고, 오래된 가격은 '과거 확인가' 또는 '재확인 필요'로 구분.
- 출처 URL이 죽었을 때도 기록 자체는 남기되 검증 상태를 표시.

## 6. 진행 순서

1. 현재 저장소를 먼저 검사하고 기존 코드·파일이 있으면 보존하면서 통합.
2. 디렉터리 구조, MD schema, API spec, 화면 플로우를 먼저 확정하고 문서화.
3. 서버의 MD validation/import/API 구현 → Next.js 모바일 도감 → 상세·비교 → 지도 → 도장/메모 순으로 개발.
4. 최소 1개 카테고리의 MD를 넣었을 때 전체 흐름이 동작하도록 만들고, **샘플 데이터는 테스트용이라고 명시**. 실제 상품 사실을 조작해서 채우지 말 것.
5. 연구 에이전트가 새로운 브랜드/모델/매장을 MD로 추가했을 때 **코드를 수정하지 않아도** UI와 API에 반영되는지 테스트.
6. 모바일 화면, 가격 옵션, 출처 링크, 매장 지도 폴백, 도장 기록 유지, 유효하지 않은 MD의 오류 처리를 검증.
7. `README.md`에 `client`·`server` 실행명령, 환경변수, 데이터 작성·추가 방법, 테스트명령, 제한사항을 작성.

## 7. 완료 조건

- 클라이언트·서버가 **서로 별도 프로세스**로 로컬에서 실행됨.
- 연구 Markdown 외부 원본만으로 도감 내용이 채워지고 상품 정보가 UI 코드에 하드코딩되지 않음.
- 침대 카테고리에서 매트리스와 프레임을 각각 탐색·비교할 수 있음.
- 새 혼수 카테고리 MD가 추가되면 새로운 도감 탭이 자동 생성됨.
- 각 모델에 이미지(없으면 플레이스홀더), 출처가 있는 가격, 장단점, 실제 후기, A/S, 방문 가능한 매장이 연결됨.
- 지도·방문 체크·체험 도장·찜·견적 메모가 작동하고 재시작해도 데이터가 유지됨.
- 검증되지 않은 가격·매장·후기를 '사실'로 제시하지 않음.
- 모바일 UI가 귀엽고 정돈되어 있으며 실제로 사용 가능한 수준임.

**중요:** 조사 에이전트와 개발 에이전트의 책임을 섞지 마세요. 제가 제공하지 않은 상품 정보는 공란으로 처리하고, 누락된 사실이 있으면 `research_requests.md`에 요청 목록만 작성하세요. 제품 리서치를 스스로 만들어 채우는 대신 사용 가능한 앱을 완성하는 데 집중하세요. 큰 기능은 자율적으로 합리적인 기본값으로 결정하고, 핵심 가정은 README에 남기세요.
